# Native packaging and provenance

`build.ps1` invokes Cargo with the committed lockfile and x86_64-pc-windows-msvc target. `build.rs` renders the app icon from `src/icons.rs`, builds a standard Windows icon/version/application-manifest resource using the Windows SDK resource compiler, and links it into the executable. The checked-in .cargo/config.toml uses Rust's standard +crt-static target feature to link the C runtime, avoiding a separate Visual C++ redistributable prerequisite. No executable payload is extracted or launched at runtime. The binary uses Windows UI/registry APIs and bundled SQLite; application code does not inject into other processes or download code.

The screenshot associated with the rewrite showed 7 of 71 vendor detections for an older executable. It does not identify their cause or prove they were false positives. The old build used PyInstaller one-file packaging and a historical spec enabled UPX. Replacing that packaging removes the Python bootloader and extraction behavior; it does not establish how a scanner will classify the new file. No multi-engine result, SmartScreen reputation, signing identity, or zero-detection claim is implied.

Each build emits `dist/build-info.json` with the Git revision, whether the source tree was dirty, UTC build time, Rust/Cargo versions, target, command, Cargo.lock SHA-256, and final executable SHA-256. A clean commit plus the lockfile identifies the reviewed source. This is build provenance, not an assertion that binaries built on different Windows SDK/linker versions are bit-for-bit identical. The executable is unsigned unless the distributor separately applies Authenticode signing; signing changes its hash and requires an updated provenance record. No signing certificate is stored in this repository.

Review source and build provenance for an unexpected detection. If a distributor chooses to submit a false-positive report, use the vendor's review process and provide the exact hash and provenance; this repository neither uploads binaries nor changes antivirus settings. Do not whitelist or disable protection as an installation step.

The G HUB database is opened using SQLITE_OPEN_READ_ONLY. SQLite handles committed WAL transactions consistently and waits at most 250 ms for a busy lock. There is no fixed-name copied database or replay of an unrelated WAL file. SQLite may use its normal shared-memory/locking sidecars for an existing WAL database; logibar does not execute database writes or schema migrations. Tests verify that database and WAL bytes remain unchanged while committed WAL readings are visible and uncommitted rows are ignored. See [SQLite WAL](https://sqlite.org/wal.html) and [rusqlite open flags](https://docs.rs/rusqlite/0.40.2/rusqlite/struct.OpenFlags.html).

Installation is explicit and per user. Ordinary portable launch sets process identity only; it does not register startup, write app-identity registry entries, clear shell caches, or restart Explorer. The tray startup action and installer use HKCU, never system-wide persistence. Sandbox mode disables startup writes and notifications, and sandbox installation redirects file changes to a validated Windows temp subdirectory. Neither scripts nor native app contain obfuscation, AV exclusions, scanner workarounds, privilege escalation, or self-extracting packers.

The MIT project license is preserved unchanged. The build walks the normal target-specific runtime dependency graph and bundles each crate's license files as third-party notices; build-only and test-only packages are not distributed. SQLite's public-domain status is stated separately. See [Windows notification icon API](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/ns-shellapi-notifyicondataw) and [resource compilation](https://docs.rs/embed-resource/3.0.12/embed_resource/) for the native packaging interfaces.
